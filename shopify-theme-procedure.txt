Работеща процедура за промени по Shopify тема (пример: test-avalon.myshopify.com)

================================================================================
FROZEN PRODUCT/CART CONTRACT (frontend → CP)
================================================================================

Product POST fields (exact):
  payload_version, source, unicid, shop_domain, shop_permanent_domain,
  variant_id, quantity

Cart POST fields (exact):
  payload_version, source, unicid, shop_domain, shop_permanent_domain,
  cart_identity

payload_version = 2. Product source = product; Cart source = cart.
Cart identity is the unmodified cart.token from the final stable cart.js
snapshot. CP reconstructs all Cart lines, quantities, catalog data,
collections, money, and currency authoritatively through Storefront Cart lookup.

Trust boundary:
  ALL frontend fields are UNTRUSTED.
  CP must validate every field server-side.
  Domains/unicid/currency/money are public context, not authentication.

================================================================================
Local financing minimum (uni_min_price) - local eligibility gate
================================================================================

Theme setting (canonical UniCredit settings block in step 5 below):
  id: uni_min_price   type: number   default: 50

Unit: whole major units of the store currency. Shopify money values
(variant price, Liquid cart.total_price, cart.js total_price) are minor units
(1/100 for the supported currencies), so the threshold is compared as
uni_min_price x 100. All comparisons are integer comparisons.

Local gate (decided in the browser, before any CP request):
  product amount = selected variant price x selected quantity
  product amount < uni_min_price  -> button hidden, no CP POST
  cart total     < uni_min_price  -> button hidden, no CP POST
  amount >= uni_min_price         -> existing eligibility continues

Dynamic visibility (slots stay in the DOM; only the hidden attribute toggles):
  Product: scoped change/input on the resolved add-to-cart form (or theme
           section) plus the one resolved quantity control, so variant and
           quantity changes both re-sync. Quantity without a usable control
           counts as 1. Liquid cannot read the theme's initial quantity, so the
           first render assumes quantity 1 and JS re-syncs on init.
  Cart:    scoped MutationObserver (childList + subtree only, never attributes)
           on the resolved Cart form, else the theme section, plus that scope's
           own change/input/submit events. Bursts are coalesced into a single
           fetchStableCart() read. No document-level observation, no polling.
  Click-time minimum checks (product price x quantity, cart total) are
  unchanged and remain the final local guard before any CP request.

Shopify "number" settings cannot enforce positive integers, so the value is
validated defensively in Liquid and again in JS: missing, zero, negative,
fractional or non-numeric configuration falls back to 50. The gate never
falls back to 0/unlimited.

This gate is local only. It does NOT change the frozen CP contracts: no
uni_min_price, price, cart amount or eligibility result is ever POSTed.

Deployment: config/settings_schema.json is intentionally NOT committed, so an
existing merchant theme must add the uni_min_price entry manually to the
UniCredit settings block from this file (step 5). No CP deployment is needed.

================================================================================
Theme compatibility policy
================================================================================

This integration is distributed to unknown Shopify stores and themes.
Do NOT assume Dawn, Horizon, or any specific theme layout.

Resolution priority:
  1. Shopify API / runtime state
     (cart.js, variants/{id}.js, products/{handle}.js, Shopify.currency, …)
  2. Platform-level form conventions
     (form[action*="/cart/add"], input[name="id"], input[name="quantity"], …)
  3. Generic defensive DOM selectors (validated; never arbitrary first match)
     e.g. input[name="quantity"], input[type="number"][name*="quantity"]
  4. Theme-specific selectors / wrappers (.shopify-section, Dawn layouts, …)
     — fallback ONLY, never primary architectural contract

When a generic selector can match more than one product context:
  validate association (form containment, form="<id>", unique page candidate).
  Do NOT pick document.querySelector(...) first match arbitrarily.

Product quantity follows this policy:
  - JET-compatible generic selectors first
    (input[name="quantity"], input[type="number"][name*="quantity"])
  - findProductForm() only disambiguates when multiple candidates exist
  - hidden/stale duplicates are dropped when a presented control exists
  - never arbitrary first match across multiple product contexts
Product price/ownership uses Ajax APIs; variant id prefers form[name=id].

Product currency and pricing are reconstructed by CP. Cart currency, discounts,
line totals, and final total are reconstructed by CP from Storefront authority.

Modal lifecycle:
  Product and Cart share one page-level active Uni flow (window.__UniTransport).
  Only one UniCredit modal may be active at a time.
  Body scroll lock/unlock is owned by the shared active flow.
  Closing an inactive modal must not alter page scroll.
  Iframe containment (Phase 8.2 theme-side):
    modal opens → loading UI → iframe created hidden
    iframe load is NOT authority to reveal
    trusted postMessage uni:ready → clear timeout, hide loading, show iframe
    no uni:ready within READY_TIMEOUT_MS (10000) → iframe stays hidden, safe parent error
  postMessage uni:ready / uni:close / uni:bank-redirect accepted only when:
    event.origin === new URL(CP_BASE_URL).origin   // derived from central config
    event.data.type === "uni:ready" | "uni:close" | "uni:bank-redirect"
    event.source === active iframe.contentWindow
  Trusted uni:bank-redirect (after SmartUCF URL validation):
    Product source → top-level SmartUCF navigation; Shopify cart untouched
    Cart source → POST {Shopify.routes.root}cart/clear.js (bounded ~2s), then navigate
    cart clear failure/timeout MUST NOT block SmartUCF redirect
    modal/Step 3 loader stays visible until navigation (no closeActive before assign)
  Close (X / Escape / uni:close) at loading|ready|timeout clears timeout, resets iframe,
  restores scroll, releases Product/Cart lock. Re-open starts a fresh attempt.

================================================================================
CP BASE URL — SINGLE SOURCE OF TRUTH (deployment packaging)
================================================================================

File:  assets/uni-transport.js
Value: CP_BASE_URL   ← change ONLY this for environment packaging

  DEV:        https://uni.avalonbg.com
  TEST:       <test CP base URL>
  PRODUCTION: <production CP base URL>

Derived automatically:
  allowed postMessage origin = new URL(CP_BASE_URL).origin
  DEV/TEST echo POST URL     = {CP_BASE_URL origin}/shopify/product-test

Do NOT put CP URL in Theme Editor / settings_schema.json.
Do NOT duplicate CP hostnames in Product/Cart JS.
Invalid CP_BASE_URL → fail safely (no modal, no POST).

Echo path /shopify/product-test is DEV/TEST ONLY.
Before production: set production CP_BASE_URL and replace echo path with
production CP routes if they differ.

SHOP-01 — Неизвестен UNICID

Какво означава:
Подаденият от темата UNICID не съответства на магазин в CP. Това обикновено е проблем в настройката на темата или CP.

Какво да проверя:
- Сравни `uni_unicid` в публикуваната Shopify тема с UNICID на магазина в CP.
- Провери дали записът за магазина съществува в CP и дали е избрана правилната тема/среда.

SHOP-02 — Магазинът не е Shopify

Какво означава:
UNICID съществува в CP, но типът на намерения магазин не е Shopify. Заявката се отхвърля преди създаване на контекст.

Какво да проверя:
- Провери типа/платформата на магазина в CP.
- Увери се, че темата използва UNICID на правилния Shopify запис, а не на друг магазин.

SHOP-03 — Несъответствие на магазин/домейн

Какво означава:
Домейнът от Shopify заявката или браузърният origin/referer не съвпада с каноничния магазин в CP. Това е отказ при обвързването или проверката на произхода.

Какво да проверя:
- Провери `shops.name`/каноничния домейн в CP спрямо постоянния `.myshopify.com` домейн и активния storefront домейн.
- Провери дали заявката идва от реалната публикувана тема и правилния магазин; виж CP логовете около посочения час.

SHOP-04 — Невалиден Shopify домейн/контекст

Какво означава:
Задължителен Shopify домейн липсва, има невалиден формат или от него не може безопасно да се определи parent origin. Това е проблем във входния контекст, преди калкулатора.

Какво да проверя:
- Провери дали текущите snippets подават `shop_domain` и `shop_permanent_domain` и дали постоянният домейн е валиден `.myshopify.com` адрес.
- Провери deployment-а на темата и CP домейн/iframe конфигурацията; не променяй защитните проверки.

SHOP-05 — Невалидна заявка или сесия

Какво означава:
Общ код за структурно невалидна заявка и за липсващ, изтекъл, повреден или чужд контекст. Включва невалиден payload/source/product или cart identity, неподдържан метод/content type, отхвърлен преход в Step 1/Back/Step 2 и несъвпадение на session ownership.

Какво да проверя:
- При първоначално отваряне провери дали актуалните theme assets/snippets изпращат payload v2 и задължителните полета.
- При Step 1, Back или Step 2 провери context TTL и session/cookie конфигурацията; не използвай контекст от друг браузър или сесия.
- Потърси точния вътрешен reason в CP логовете по магазин и час.

SHOP-06 — Надвишен лимит на заявките

Какво означава:
Достигнат е публичен или downstream лимит за заявки, или limiter backend не може безопасно да разреши заявката. Финансовият lifecycle не започва.

Какво да проверя:
- Изчакай според `Retry-After` и провери за повтарящи се заявки от същия клиент/магазин.
- Провери CP логовете и състоянието на cache/limiter услугата; не изключвай защитата, за да заобиколиш кода.

SHOP-09 — Вътрешен или Storefront проблем

Какво означава:
Общ код за неочакван CP проблем или невъзможност да се възстанови авторитетното Product/Cart състояние от Shopify Storefront. Използва се още при липсващ магазин след създаден контекст и при някои вътрешни lifecycle откази.

Какво да проверя:
- Потърси `shopify_financing_internal_error` и съответния `internal_reason` в CP application логовете.
- При Product/Cart authority провери Storefront token/config, достъпа до Storefront API, variant/cart съществуването и мрежовите/GraphQL отговори.
- При Step 1/Back/Step 2 провери текущия CP запис на магазина, базата данни и lifecycle зависимостите; кодът е широк и логът определя конкретната причина.

FIN-01 — Няма конфигурирани схеми

Какво означава:
Режимът на калкулатора изисква схеми, но административният inventory е празен. Магазинът е разпознат, но няма какво да бъде предложено.

Какво да проверя:
- Провери режима на калкулатора и конфигурираните/активни схеми и KOP филтри в CP.
- Потвърди, че схемите са записани за правилния магазин.

FIN-02 — Няма приложима оферта

Какво означава:
Има конфигурирани схеми, но нито една не е приложима за текущата покупка. Причината може да е сума, валута, дата, продукт/колекция, срок или празно пресичане на допустимите схеми в количката.

Какво да проверя:
- Сравни сумата и валутата на покупката с минималните/максималните стойности и валутната настройка в CP.
- Провери периодите, продуктите/колекциите, сроковете и KOP филтрите; при количка провери дали всички редове имат обща допустима схема.

FIN-03 — Невалидна конфигурация за изчисление

Какво означава:
Схеми има, но калкулаторът не може да изгради валидни оферти. Реалните варианти включват неподдържан режим, липсващ coefficient list или невалидни коефициенти/стойности при изграждането на оферта.

Какво да проверя:
- Провери `uni_typekop`, coefficient list и конфигурацията на съответните схеми/KOP в CP.
- Виж `shopify_financing_configuration_error` и `internal_reason` в CP логовете, за да различиш конкретния вариант.

FIN-04 — UniCredit модулът е изключен

Какво означава:
Магазинът е валидиран, но UniCredit модулът не е активен в текущия CP запис. Проверката се прави при входа и отново при Step 1, Back и Step 2.

Какво да проверя:
- Провери дали `shops.uni_status`/статусът на UniCredit модула е активен за правилния магазин.
- Ако модулът е изключен умишлено, не предприемай промяна; ако не е, провери кой и кога е променил настройката.
